# 리버트(Revert) 정리

> 트랜잭션이 "블록에는 들어갔는데 실행은 실패한" 상태 — 가이드 6번 섹션의 **유형 ③**.
> 실습 스크립트: `src/ethereum/03-fail.ts`

---

## 한 줄 요약

**리버트 = "계산은 다 해봤는데 조건이 안 맞아서, 결과만 없던 일로 하는 것."**
계산에 들어간 비용(가스비)은 환불되지 않습니다.

| | ① 접수 거부 | ③ 리버트 |
|---|---|---|
| 누가 막나 | RPC 노드 | 컨트랙트 로직 |
| 언제 | 보내자마자 | 블록에 들어간 뒤 |
| 가스비 | 0 | **소모됨** |
| tx hash | 없음 | 있음 |
| 코드에서 | `throw` (catch로 잡힘) | `receipt.status === 'reverted'` |
| 비유 | 서류 미비로 반려 | 상담비 내고 심사 부결 |

---

## 1. 왜 실패했는데 돈을 내나

**결론: 검증자가 실제로 일을 했기 때문입니다.**

트랜잭션이 블록에 들어가면 전 세계 검증자들이 내 요청을 진짜로 실행해봅니다.
실행해보기 전에는 성공할지 실패할지 알 수 없기 때문입니다.

- *비유:* 변호사 상담과 같습니다. 계약이 성사되든 무산되든 상담한 시간만큼 수임료를 냅니다.
- 가스비는 **결과에 대한 대가가 아니라 계산에 대한 대가**입니다.

반면 유형 ①(접수 거부)은 창구에서 서류를 보고 바로 돌려보낸 것입니다.
아무도 일을 안 했으니 비용도 없습니다.

---

## 2. 구체적 시나리오 — NFT 민팅

컨트랙트에 이런 조건이 걸려 있다고 합시다.

```solidity
require(남은수량 > 0, "SOLD_OUT");   // 매진이면 중단
```

| 시각 | 사건 |
|---|---|
| 14:00:00 | 남은 수량 1개. 내가 민팅 트랜잭션 전송 |
| 14:00:03 | 다른 사람이 더 높은 가스비로 먼저 채감 → 남은 수량 0 |
| 14:00:12 | 내 트랜잭션이 블록에 들어가 실행됨 |
| 14:00:12 | `require` 조건 불충족 → **리버트** |

**결과**

```
NFT     : 못 받음
가스비  : 0.004 ETH 소모 (약 1만원)
tx hash : 있음 (Etherscan에서 조회됨)
receipt : status = 'reverted'
nonce   : 올라감
```

돈만 나가고 얻은 건 없습니다. 인기 NFT 민팅 때 수백 명이 동시에 겪는 상황입니다.

## 3. 코드에서 어떻게 보이나

**결론: 에러가 안 납니다. 그래서 위험합니다.**

```ts
const hash = await sendRawTransaction(...)        // ✅ 통과
const receipt = await waitForTransactionReceipt() // ✅ 통과
console.log('전송 완료!')                          // 😱 여기까지 그냥 옴
```

`try/catch`로도 못 잡습니다. 예외가 아니라 **정상 응답에 담긴 실패**이기 때문입니다.

반드시 이렇게 확인해야 합니다.

```ts
if (receipt.status === 'reverted') {
  // 실패 처리
}
```

- *FE 비유:* HTTP 200 응답인데 body에 `{success: false}`가 들어있는 상황입니다.
  상태 코드만 보면 성공으로 착각합니다.

---

## 4. "되돌려진다"의 범위

**결론: 그 트랜잭션이 건드린 모든 상태 변경이 통째로 취소됩니다.**

컨트랙트가 10줄을 실행하다가 7번째 줄에서 실패했다면,
1~6번째 줄이 바꿔놓은 것도 전부 원상복구됩니다.

```
1. 수량 차감      ← 취소
2. 소유권 기록    ← 취소
3. 이벤트 발생    ← 취소
4. require 실패   ← 여기서 중단
```

이걸 **all-or-nothing(원자성)** 이라고 합니다.
"절반만 처리된 상태"가 생기지 않도록 하는 안전장치입니다.

- *비유:* 은행 이체에서 "출금은 됐는데 입금이 안 된" 상태가 생기면 안 되는 것과 같습니다.

**단, 가스비는 예외입니다.** 가스비는 컨트랙트 로직이 아니라 네트워크 요금이라 되돌려지지 않습니다.

---

## 5. 어떻게 막나

**결론: 보내기 전에 미리 실행해봅니다.**

```ts
await publicClient.simulateContract({ ... })
```

내 요청을 체인에 올리지 않고 노드에서 흉내만 내보는 것입니다.
실패할 거면 여기서 에러가 나고, 가스비는 한 푼도 안 나갑니다.

**실무 순서**

```
1. simulate   → 실패하면 여기서 중단 (가스비 0)
2. 성공하면 → 서명 → 전송
3. receipt.status 반드시 확인
```

1번을 빼먹는 게 초보자가 가장 많이 하는 실수입니다.

> ⚠️ 시뮬레이션이 성공해도 실제 전송 때 실패할 수 있습니다.
> 위 NFT 예시처럼 그 사이에 체인 상태가 바뀔 수 있기 때문입니다.
> 확률을 줄이는 장치지 보장은 아닙니다.

## 6. 솔라나는 어떻게 다른가

**결론: 개념은 같지만, 솔라나는 "실패를 미리 걸러주고 실패 비용도 훨씬 싸다."**

| 항목 | 이더리움 | 솔라나 |
|---|---|---|
| 실패해도 수수료 | 나감 (실행량 비례) | 나감 (**고정 base fee**) |
| 실패 비용 규모 | 0.001~0.01 ETH (수천~수만원) | 0.000005 SOL (**0.1원 미만**) |
| 사전 시뮬레이션 | 개발자가 직접 호출해야 함 | **기본으로 켜져 있음** (preflight) |
| 에러 형태 | `revert reason` 문자열 (`"SOLD_OUT"`) | `Custom(N)` 숫자 코드 |
| 원자성 | 트랜잭션 단위 | 트랜잭션 단위 (명령어 여러 개도 전부 취소) |
| 고유 실패 유형 | `nonce too low` | `BlockhashNotFound` (유효기간 만료) |

### 차이 1 — 사전 시뮬레이션이 기본값

솔라나의 `sendTransaction`은 **preflight 시뮬레이션을 자동으로 돌린 뒤** 전송합니다.
실패할 트랜잭션은 RPC 단계에서 걸러지므로, 이더리움식 "리버트 사고"가 훨씬 적습니다.

- 이더리움: `simulateContract`를 **내가 호출해야** 함 → 빼먹으면 가스비 날림
- 솔라나: 기본으로 해줌 → `skipPreflight: true`로 꺼야 통과됨

즉 솔라나에서 리버트를 일부러 보려면 preflight를 끄거나, 시뮬레이션 이후에 체인 상태가 바뀌어야 합니다.

### 차이 2 — 실패 비용의 체감이 다름

이더리움은 가스를 쓴 만큼 냅니다. 복잡한 컨트랙트가 중간에 실패하면 그만큼 비쌉니다.
솔라나는 서명 1개당 5,000 lamports(= 0.000005 SOL) 고정이라, 실패해도 사실상 무시할 수준입니다.

그래서 **"실패하면 가스비가 아깝다"는 긴장감이 솔라나에는 거의 없습니다.**
이더리움 실습에서 이 감각을 익혀두는 게 중요한 이유입니다.

### 차이 3 — 에러 메시지를 읽는 법

- 이더리움: `execution reverted: SOLD_OUT` — 사람이 읽을 수 있는 이유가 붙음
- 솔라나: `Custom(6001)` — 숫자만 옴. **해당 프로그램의 에러 코드표를 찾아봐야** 뜻을 앎

솔라나 쪽이 디버깅 난이도가 높습니다.
